#### Why Use Design Patterns? 
Developing *Object Oriented Code* is a relatively hard task as you're trying to create a design that effectively solves the problem but is also general enough to accommodate future problems and avoid redesigns. 
One reason why *OO Experts* are known as *experts* is because of the fact that they **reuse solutions** that have worked for them in the past. This develops into a beautiful pattern of reusable modular code that can be effective for a certain type or subset of problems. e.g. Playwrights and novelists never write a plot from scratch, instead they use patterns like "Tragically flawed hero" or "The Romantic Novel" etc. something similar can be done to make Object Oriented Programming easier. 
#### Formal Definition 
	A pattern describes a problem which occurs over and over again in our environment and then describes the core of the solution to that problem, in such a way that you can use this solution a million times over, without ever doing it the same way twice.
#### Components
* The *component name*: A handle used to describe a problem, it solution and consequences in a word or two. 
* The *problem* describes when to apply this certain design pattern. It explains it and its context. 
* The *solution* describes elements that make up the design, their relationships, responsibilities and collaborations. 
* The *consequences* are the results and trade offs of applying this pattern.

#### Classification and Selection 
* Creational: Deals with object creation (e.g. Factory Method, Singleton)
* Structural: Focuses on class/object composition (e.g. Adapter, Composite) 
* Behavioural: Manages object interaction (e.g. Observer, Strategy)
#### Benefits 
* *Reusability*
* *Scalability*
* *Readability*
#### Drawbacks
* *Over-engineering*
* *Learning Curve*
* *Performance Overhead*
